# 桌面使用说明

## 启动与分发

使用 Windows 10/11 64 位。把单个 `TKChatWave.exe` 放到可写位置后双击即可。发布版已经内置 Python、Qt 和 Chromium；首次运行会在 EXE 同级创建 `runtime/`。移动 EXE 前先退出程序，已有账号要继续使用时应同时移动原来的 `runtime/`。只把 EXE 发给别人时，不会携带你本机已有的 Cookie。

发布版自带 Chromium 和 Python/Qt 依赖，不依赖已安装 Chrome。若 EXE 被安全软件隔离或损坏，应重新获取完整的单文件发布版。源码运行、依赖安装与构建步骤见 [README](../README.md)。

同一 Windows 用户只能运行一份程序，即使 EXE 位于不同文件夹。重复启动只唤起已有窗口，不再初始化另一份账号库或开始业务任务；已有程序正在退出时请等待安全收尾。异常退出后的锁会在下次启动时检测恢复，不需要删除账号文件。程序先检查数据目录是否可写，失败时弹出脱敏的处理提示，不会自动迁移、重置或删除数据。

对外分发请使用 `releases/` 中生成的干净 ZIP。解压后只有 `TKChatWave.exe`、`使用说明.txt` 和 `版本信息.json`；版本信息包含 EXE 的 SHA-256。不要把本机整个 `dist/` 或 `runtime/` 压缩给别人。更新前退出程序，仅替换 EXE，保留原 `runtime/`。

## 新增或更新账号

点击“新增 / 更新账号”。程序每次都会打开一个新的无痕 Chromium 登录窗口，可正常最大化、缩放和滚动；在 TikTok 官方页面选择当前提供的二维码、手机号、邮箱、Google、Facebook 等方式。Google/Facebook OAuth 可能继续打开独立窗口。实际登录选项、额外验证及可用性由平台决定。

完成登录并等待返回 TikTok 页面。程序检查关键登录 Cookie、`s_v_web_id` 和稳定的完整登录状态后才原子保存账号；默认等待上限为 300 秒。同一 TikTok UID 再次登录时更新已有记录，账号区仅显示用户名、短 ID 和状态。程序会在关闭无痕浏览器前读取当前登录 Cookie、UA 与配套会话材料，并原子保存到账号库；无痕模式只阻止 Chromium 自己长期保留会话，不会丢失工具已经保存的 Cookie。登录结束后浏览器关闭。

“新增 / 更新账号”只保存账号，登录成功后不会自动发送。账号库为空或没有勾选发送账号时，“开始发送”不可用；保存账号后需勾选并主动开始发送。点击“停止”或关闭浏览器会取消未完成登录，不写入不完整账号；登录超时也不会保存本次登录。若取消发生在账号已经成功保存之后，已完成的保存会保留。

删除账号前会显示用户名并要求确认，默认按钮为“取消”，关闭确认框或按 Escape 均不删除。确认删除仅移除本机保存的登录记录，不注销 TikTok 账号；再次使用需重新登录。

## 账号详情与运行设置

选中账号后点击“查看详情”，或双击账号行，可查看并手动修改该账号在本机保存的完整 JSON，包括 Cookie、UA、环境信息和 Ticket Guard 会话材料。点击“保存”前请保持 JSON 格式正确；账号 ID 不可修改，Cookie 必须保留有效的 TikTok 登录标识。若登录或其他操作已更新该账号，旧详情窗口不能覆盖新数据，需重新打开。内容高度敏感，不要截图、复制给他人或随发布 EXE 分发。

点击右上角“设置”可调整登录超时、账号启动错峰间隔、心跳发送间隔、是否启用弹幕展示确认、是否显示弹幕、观察超时、每条消息总尝试次数和重试间隔、监听连接超时/重试，以及 roomId 兜底 Cookie。账号仍并发，错峰只控制启动时间，0 秒同时启动；每条消息总尝试次数包含首次发送，临时故障和未展示重发共用上限。设置保存到 `runtime/desktop-settings.json`，重启后继续生效；主界面的目标用户名和消息仍是每次发送前填写的必填项。

## 发送、停止与退出

先在账号表的“发送”列勾选本轮要发送的账号，可用“全选 / 清空选择”快速调整；点击账号行用于查看详情或删除，与发送勾选无关。刷新账号列表会保留仍存在账号的勾选状态。填写目标主播的用户名（例如 `creator` 或 `@creator`，不是昵称或完整链接），多个直播间用英文 `;` 或中文 `；` 分隔，例如 `A;@B;C`。自动去除首尾空白和一个前导 `@`，忽略空分段，按不区分大小写去重并保留首次出现顺序。任何一个目标非法时整轮不能开始，避免部分输入已发送后才发现错误。空目标、仅 `@` 或空白消息同样不能开始。点击“开始发送”后，目标、正文、次数、间隔、账号编辑与勾选和运行设置暂时锁定，“停止”仍可用，后台工作不会阻塞界面。

程序只处理本轮勾选且去重后的已保存账号，不在发送前打开浏览器预校验。运行设置 → 基础 → 直播间执行方式可选串行或并行，保存后下次运行继续使用。默认串行：每个账号独立按填写顺序执行房间列表，完成当前房间并关闭自己的连接后直接进入下一房间，不等待其他账号；同一账号同时只处理一个房间，不同账号可以位于不同房间。并行：最多同时执行 3 个直播间，其余排队；一个房间的全部账号结束后才释放房间名额，房间内全部已选账号并发处理。只有一个直播间时，两种模式均按账号并发。并发会增加线程、网络连接和内存占用，选中账号越多占用越高；请按本机和网络条件选择账号数量。任务运行时只能查看设置，不能中途切换模式。每个账号任务使用独立临时账号快照，收尾时再合并允许的账号变更，报告也按本轮、房间和账号隔离。详情窗口始终按填写顺序显示每个房间的独立结果，不按完成先后重新排序。

账号列表有独立的上下滚动条，默认预留约两行账号空间，随账号数增至约四行，也可点击“展开账号区”。上方内容与日志区之间可拖动调整高度；窗口缩放时重新分配空间，优先为日志保留至少约三分之一窗口高度。消息框压缩为约两行并占满内容行，次数和间隔在其下方同排左对齐；宽窗口下账号操作和统计卡片各压成一排，减少留白。800×700 等较小窗口、账号较多或展开账号区后空间不足时，可滚动查看上方内容，日志保持可用。日志右下角的“清空控制台”只清除当前窗口内容，每日文件仍保留。普通网络失败、403 或非登录类响应不删除账号；只有接口明确要求重新登录时才移除对应失效账号。进度卡累计所有账号、所有房间已经完成的实际消息请求结果。

结束提示区分“完成”“失败”“已停止”，同时列出已观察到消息、已接受但未观察到、监听不可用的计数。失败房间或账号不会显示为全成功；失败与取消同时发生时优先显示失败，保留已完成计数。状态栏显示前 3 个房间的结果，全部房间的安全摘要在运行日志中。“完成”仅代表任务已收尾，接口接受不代表已公开展示。

“停止”是协作取消：设置取消标记，阻止排队房间启动及后续消息 POST；不能撤回已发出的消息。进行中的网络请求、连接或弹幕等待需要先返回，因此不是立即中断。预热和发送间隔可提前结束；后台会等待各房间和账号资源收尾。已完成计数与账号保存保留。

关闭窗口同样请求停止并清理监听与浏览器。窗口若显示“正在退出”，应等待后台操作结束；一次约 2 秒的等待预算不是强制终止时间，仍运行的线程会保留并继续清理。

## 发送次数与展示确认

消息框下方提供独立同排的“发送次数”和“发送间隔”。次数表示每账号每直播间发送次数，默认 1，可填写正整数，已取消 100 次上限；间隔默认 1 秒，范围 0.1–3600 秒，表示同一账号在同一房间相邻请求完成后等待的时间。这些输入在运行期间锁定。计划请求总量 = 已选去重账号数 × 去重直播间数 × 发送次数，例如 2 个账号、3 个房间、每账号每直播间 4 次，最多 24 次消息请求；失败或停止可能使实际请求数减少。不同账号或房间可同时发送，间隔不是全局限速。串行模式不限制目标直播间数量，各账号按列表逐个执行一遍，自身连接清理完就进入下一房间；不无限循环列表。

每个账号在每个房间各建立一次独立账号 WSS 心跳连接，持续覆盖该账号在对应房间的全部发送和弹幕确认，结束、停止或异常时统一关闭。建立连接前，工具使用该账号当前 Cookie 和同一套 UA 身份依次执行 HTTP 进房、首次 `/webcast/im/fetch/`，再使用首次响应中的服务端 WSS 地址、路由参数和 cursor 建立账号连接；首次 fetch 使用 `urlencode(..., doseq=True)` 编码且只发送一次 `version_code=270000`，并为本次请求重新生成签名。请求头 UA、签名 UA 和 `browser_version` 始终一致。任一步失败都会在消息 POST 前停止，不使用静态 WSS 地址或空 cursor 继续发送。

心跳发送间隔默认 10 秒，可设为 1–60 秒，同时应用于账号及访客连接。首次连接后等待“间隔×3”秒，成功发送至少 3 次目标房间心跳且跨度至少“间隔×2”秒，并收到进房响应才发送；预热超时为预热时长加上“10 秒与心跳间隔中的较大值”。例如间隔 5/10/20 秒时预热至少 15/30/60 秒。连接或预热失败按设置重试。后续消息复用该账号该房间的连接、HTTP Session 和 roomId，不重复预热；连接中途断开则停止后续发送。每次实际发出的心跳记录 `wss_heartbeat_sent`，失败记录 `wss_heartbeat_send_failed`，不打印包内凭据。访客观察到对应弹幕后记录绿色“消息成功展示”；仅接口接受但未观察到时不标记展示成功。

桌面模式严格按选定次数执行，未观察到弹幕不会额外增加发送次数；明确失败、禁言、登录失效或手动停止会提前结束当前账号剩余发送。发送和弹幕确认分阶段进行，确认等待不会插入相邻两次发送之间。接口返回消息 ID 时，展示确认还要求弹幕 ID 一致，避免相同内容重复计数。进度卡按实际消息请求计数。

默认 `MESSAGE_NOT_OBSERVED_RETRIES = 1`：每条消息只发送一次，不自动重发。需要时可在工具设置中调整“每条消息总尝试次数”，次数包含首次发送；例如设为 3 表示最多尝试三次。已有自定义设置不自动覆盖。设置大于 1 时，符合条件的临时故障和未观察到消息会共用此上限；后续请求复用已准备的会话，并重新生成消息时间戳与签名。明确失败、禁言、封禁不会触发重发。

监听器连接次数是另一项配置：`MESSAGE_OBSERVER_CONNECT_RETRIES = 3` 表示首次连接加最多三次重试，总共最多四次。连接失败后会继续原消息请求，记录“监听不可用”；这不保证消息公开展示。

监听只考虑本次请求起始时间之后的事件，并匹配规范化后的消息正文（NFKC、去除首尾空白和表情展示选择符）。当前继承的身份规则是：预期账号用户名匹配事件的 `unique_id` 或 `nickname`，**或者**事件数字 UID 匹配账号的预期 UID；名称会去除首尾空白、前导 `@` 并忽略大小写。即使已保存用户名，也接受 UID 匹配；用户名/昵称匹配时不会再要求 UID 一致。旧账号通过观察获得 `unique_id` 时可将其写回账号库。

此规则存在昵称碰撞限制：另一用户若昵称与预期用户名相同，并发送相同正文，即使其 `unique_id` 和 UID 均不同，也可能被计为 `delivered`。因此该计数只表示当前匹配规则找到了事件，不是严格的发送者身份证明；需要可靠验收时还应在观众端核对实际发送者。发送端本地显示或接口 HTTP 200 也不能证明其他观众收到弹幕。本次文档修订不改变这项继承行为，严格身份匹配需单独设计与回归验证。

| 界面 / 字段 | 含义 |
| --- | --- |
| 已处理 / `processed` | `success + failed + expired + temporaryError`；桌面模式按消息请求计数，CLI 兼容模式按账号计数。 |
| 接口成功 / `success` | 明确成功的请求，或需要观察的响应最终获得弹幕确认；不能单凭此卡证明公开展示。 |
| 已观察到消息 / `delivered` | 本次等待内收到符合当前正文和名称或 UID 规则的事件；昵称碰撞可造成误判，不能作为严格发送者证明。 |
| 已接受 / 未观察到 / `acceptedNotObserved` | 完成观察/重试后仍无匹配弹幕；成功响应通常计入 `success`，不确定评论响应计入 `failed`。取消重试时也可能保留此结果。 |
| 失败 / `failed` | 网络、解析或业务失败，以及未能确认的不确定评论响应；保留非过期账号。 |
| 登录失效 / `expired` | 接口明确要求重新登录；仅移除对应账号，重新新增可恢复。 |
| 疑似禁言 / `silenced` | 识别到 `account_silenced` 响应；它也是失败的附加分类，不另计一个已处理账号。 |
| 监听不可用 / `listenerUnavailable` | 监听未连接，消息流程继续但展示无法确认；普通成功仍计 `success`，不确定评论响应计 `failed`。 |
| 临时错误 / `temporaryError` | 保留的兼容计数，当前发送流程的网络错误通常计入 `failed`。 |

结果分类与展示计数有重叠，不要把所有卡片相加作为账号总数。账号任务在请求前异常也会使房间和整轮失败，但不会凭空增加“已处理”或消息“失败”计数。`4010048` 且提示“由于本场直播的设置，无法发布评论”时按 `room_comment_restricted` 记录，停止本房间所有账号的后续发送，不观察或重试该响应；已在途的请求不能撤回。串行时清理后处理下一房间，并行时不影响其他房间。禁言响应按 `account_silenced` 记录，停止该账号后续发送。消息总尝试次数默认 1，不自动重发；用户可在设置中调整，已有设置不会被覆盖。

同一账号在同一直播间本轮连续 3 条不同消息出现 `accepted_not_observed`，触发 `consecutive_not_observed`，停止该账号在该房间尚未开始的发送及重试，日志和展示详情显示“连续未确认停发”。这是展示确认保护，不是认定禁言。中间出现成功展示或其他结果会清零；同一条消息的重试、重复日志不重复累计，成功的重复通知也不反复清零。第 3 次触发前收到的迟到成功会清零；保护一旦触发，本轮不自动恢复。计数不跨账号、不跨房间、不跨重新开始任务保留。已经在途的请求不能撤回，完成后仍照常计入发送和展示结果；不会把未发送的计划条目凭空计为失败。

fetch 日志只显示域名和路径，全部查询参数均不打印，实际请求和签名参数不因此删改。每套账号/房间请求流程随机选择一次 curl_cffi HTTP 传输指纹，流程内各会话和重试复用；并行任务独立选择，随机结果允许相同。指纹池包含用户指定的 23 种 Chrome、Safari、Firefox 配置；这只改变传输配置，不更改账号保存的 UA、签名 UA、`browser_version` 或 Cookie，也不保证能避免平台风控。

## 数据位置与隐私

桌面模式在项目目录（源码）或 EXE 同级（发布版）创建：

```text
runtime/
├─ accounts/tiktok_accounts.json
├─ desktop-settings.json
├─ profiles/<随机本机调试端口>/
├─ reports/run-<随机批次标识>/<房间序号>/<账号序号>/failed_accounts.json
├─ reports/run-<随机批次标识>/<房间序号>/<账号序号>/silenced_accounts.json
└─ logs/YYYY-MM-DD.log
```

账号库含完整 Cookie、登录浏览器 UA、环境种子及登录时生成的 Ticket Guard 请求头/会话材料；后续请求按账号复用这些值；profile 也含登录数据。账号库使用同目录临时文件与原子替换，历史 Cookie 数组可读取并在下一次保存时转为单个字符串。桌面与 CLI 默认库、原项目库彼此独立，不自动导入。

失败报告只含短 ID、用户名、固定分类；禁言报告还可含业务状态码。并发桌面模式每次运行创建独立的随机批次目录，内部以房间和账号序号隔离报告，避免并发覆盖；单个任务正常完成/协作停止时原子写入对应报告，没有记录则写空列表。批次目录会保留历史记录。登录阶段、早期校验错误或异常退出可能没有生成新报告，应结合文件时间与日志判断。CLI 仍使用其原报告位置。日志按本地日期分别追加保存。消息正文和账号用户名可能出现在日志中。

完整 Cookie、`msToken`、CSRF、签名与 Ticket Guard 私密值不会写入运行日志；用户主动打开“查看详情”时会在本机编辑窗口显示完整保存记录。发布扫描排除账号库、profile、历史报告/日志和实际凭据；发布目录不包含开发账号。请勿把使用后的 `runtime` 打包给其他人，也不要公开账号库/profile 或把凭据填入消息。诊断时只分享必要的脱敏分类与计数。

## 排障

请求顺序、每个发送前失败点、`initial_fetch_unavailable` 的细分原因和脱敏诊断字段，参见 [直播间消息请求链路与失败点](live-message-failure-points.md)。

登录日志会依次记录 `login_browser_starting`、`login_browser_ready`、`login_detected`、`login_capture_complete`、`browser_closing` 和 `browser_closed`。采集完成后仍保留 10 秒等待；常规关闭失败时，仅对本次独立 profile 和调试端口对应的浏览器进程树进行兜底清理，不结束其他 Chrome 窗口。若仍无法关闭，记录 `browser_close_failed` 并提示手动处理，不保存本次登录。`login_finished` 的 `status=saved/failed/cancelled` 区分保存成功、失败及取消，单独出现“登录操作结束”不等于成功。

两个 WSS 连接用途不同：`role=delivery_observer` 为公开弹幕展示监听，`role=account_heartbeat` 为发送账号的进房与心跳连接；它们不是两次消息发送。

每条消息分别记录房间、账号用户名、短 ID、消息序号、消息 ID 和展示状态。以下仅为虚构示例，多房间和多账号运行时日志可能交错：

```text
消息展示观察结果 | room=A | account_username=viewer_one | account_id=123456abcdef | message_index=1/4 | message_id=10001 | display_status=observed | classification=delivered
消息展示观察结果 | room=B | account_username=viewer_two | account_id=abcdef123456 | message_index=1/4 | message_id=10002 | display_status=not_observed | classification=accepted_not_observed
消息展示观察结果 | room=A | account_username=viewer_two | account_id=abcdef123456 | message_index=2/4 | message_id=- | display_status=listener_unavailable | classification=listener_unavailable
消息展示观察结果 | room=B | account_username=viewer_one | account_id=123456abcdef | message_index=2/4 | message_id=- | display_status=send_failed | classification=send_failed
```

`observed` 表示观察到匹配事件，对应 `classification=delivered` 及 delivered 计数；`not_observed` 表示未观察到匹配展示；`listener_unavailable` 表示监听不可用或关闭，不能判断展示；`send_failed` 表示本条发送失败。响应内容先脱敏，再只显示前 150 字；消息 ID 缺失时使用 `-`。

| 现象 | 处理 |
| --- | --- |
| 账号库缺失、零字节、空白或空列表 | 视为空库。请先点击“新增 / 更新账号”完成登录；点击“开始发送”只会提示添加账号，不会自动打开登录页。 |
| `account_store_corrupt` / `account_store_unreadable` | 损坏不会自动覆盖。关闭程序后私下备份文件，检查权限，恢复已知完好的备份；没有备份时保留损坏文件后重新登录建库。 |
| `account_save_failed` | 检查 runtime 的写权限、空间和文件占用；不要因此重复发送已成功处理的账号。 |
| `login_cancelled` / `login_timeout` | 本次未完成登录不保存；重新新增并在 300 秒内完成官方流程。 |
| 缺关键 Cookie、`s_v_web_id` 或页面未跳转 | 等待完整页面加载，检查网络，重新登录；不要手工拼接 Cookie。 |
| `ticket_guard_unavailable` | 当前账号缺少有效配套 Ticket Guard 状态，本次未发送消息；新增/更新该账号后重试。账号会保留。 |
| `initial_fetch_unavailable` | HTTP 进房后的首次直播数据请求未成功，或响应中缺少可用的 WSS 地址、路由参数/cursor；工具会在连接心跳和发送消息前停止。检查直播状态、账号登录态、网络及 UA 一致性后重试。 |
| `chromium_unavailable` | 检查完整随包浏览器及 Windows 桌面会话。源码模式还需检查 DrissionPage 和浏览器路径。 |
| `listener_unavailable` | 检查主播是否开播、直播弹幕流网络与地区可访问性；消息流程仍可能继续，只能说未确认展示。 |
| HTTP 403、429 或平台风控 | 停止快速重试，检查合法账号状态与网络，等待后再尝试；普通失败保留账号，不等于登录过期。 |
| `accepted_not_observed` | 接口接受不等于公开展示。检查评论过滤、主播静音、账号限制与网络延迟，减少频率；用其他观众端交互确认，不反复运行。 |
| `4010048` 且提示“由于本场直播的设置，无法发布评论” | `room_comment_restricted`：停止本房间后续发送并清理连接，不影响其他房间；不能据此认定房间关闭。其他提示不套用这项房间级判断。 |
| `account_silenced` / 疑似禁言 | 查看禁言报告与主播/管理员状态；本轮不重试该消息，账号仍保留。 |
| `roomExists=False` / 直播间不存在 | 检查用户名、直播状态、地区访问；网络或风控本身不能证明房间不存在。 |
| 登录页慢、弹幕流不稳、停止较慢 | 确认网络/代理同时允许官方页面、OAuth 服务、HTTP 请求和直播连接；避免不稳定代理与频繁换出口，等待进行中操作返回。工具没有独立代理设置界面。 |

## 验收范围

### 运行中查看与消息展示标记

发送或登录任务运行时，可选择账号行并打开“查看详情”和“运行设置”。
窗口以只读方式展示；已打开的窗口也会同步锁定编辑和保存，任务结束后恢复。
账号增删、发送勾选和任务输入在运行中仍然锁定，查看不会改变本次任务。

账号表最右侧“消息展示”按本轮该账号所有目标直播间的计划消息总数汇总：

- 绿色勾：计划消息全部被旁观监听确认，例如“已展示 3/3”。接口成功本身不会变绿。
- 红色叉：该账号所有房间均已结束且全部明确失败，没有接口接受、展示成功或展示不确定的结果。
- 橙色：部分展示、接口已接受但未观察到、监听不可用，或其他未确认状态；不等于消息一定不可见。
- 蓝色：正在运行，显示累计已发送和已展示条数；已结束房间的失败不会盖住其他房间的运行状态。
- 灰色：未测试、等待执行，或主动停止且没有其他失败/展示结果。

连续未确认停发但已展示部分消息时显示橙色“部分展示”，保留停发原因。状态列同步显示“正在运行 / 等待执行 / 已结束”。

旁观 WSS 曾成功连接后意外断开，同一监听任务最多自动重连 3 次，每次间隔 1 秒，连接超时沿用监听连接超时设置。重连复用独立访客会话和原房间，不使用发送账号登录态，不重新发送消息。断线期间缺失的展示证据记为 `listener_unavailable`，不计入连续 3 条 `accepted_not_observed`；已完整观察结束的结果不会因后续断线改判。重连成功后继续接收弹幕；耗尽次数仍保留“无法确认”，不能因此判定消息不可见。结束任务或离开房间会取消重连、关闭连接并等待监听线程退出。

点击“消息展示”列可打开只读详情窗口，按直播间查看展示计数、失败阶段和安全错误分类；运行中会同步更新。详情不展示 Cookie、令牌或原始异常。
重复进度事件不会重复累计，刷新账号表保留结果；下次开始发送时清空上一轮结果。
标记只保留在当前程序会话，不写入账号 Cookie 文件。

运行日志提供“全部级别 / 成功 / 警告 / 错误”筛选和不区分大小写的关键词搜索，两者可以组合。错误包含严重错误；成功仅表示观察到消息展示。
界面缓存最近 2000 个非空日志行，先脱敏再缓存。筛选不会改变每日日志文件；“清空控制台”同时清除当前界面缓存，取消筛选不会恢复已清空内容。
运行日志右侧提供常驻滚动条。上翻查看历史时自动取消“跟随最新”，重新勾选后恢复跟随；筛选功能在任务运行中仍可使用。
日志按本机日期保存在 EXE 旁的 `runtime/logs/YYYY-MM-DD.log`，同一天重启继续追加，跨天自动切换文件，不再按大小分卷。每轮发送结束（含失败或停止）和登录操作结束时会显示完整保存路径。历史 `desktop.log` 保留不动；日志仍会过滤凭证信息。

离线回归、受控并发和启动/冻结包冒烟不替代真实平台登录与公开展示验收。交互验收由用户选择自己的账号、具体获授权目标直播间和具体消息后进行：先通过新增按钮只登录保存，验证独立浏览器中的实际登录方式及 OAuth 新窗口，再确认账号数。真实发送前核对“账号数 × 去重房间数 × 每账号每直播间次数”，并检查分类、报告、停止与退出，不打印账号 JSON。桌面模式不会因未观察到展示而额外发送。

当前源码中的“HTTP 进房 → 首次 fetch → 服务端 WSS 路由/cursor → 进房响应和持续心跳 → 消息 POST → 独立旁观确认”链路已经在一次用户明确授权的在线直播间完成端到端展示验收，旁观事件的消息 ID 与发送接口返回值一致。该结果证明本次实现链路可用，但不代表所有账号、直播间、网络出口、登录/OAuth 或另一台干净 Windows 电脑都已验收；平台状态变化时仍应按上述流程重新核对。
