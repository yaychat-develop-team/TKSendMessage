# First-party webcast initialization instead of TikTokLive sign service

## Goal and scope

Replace the missing TikTokLive `fetch_signed_websocket(client_enter=True)` initialization in the existing direct-WSS implementation with TikTok's first-party web initialization request. Keep chat POST, room lookup, account selection, observer matching, and UI behavior unchanged. The final runtime must not call a third-party signing service or drive a browser to send messages. A successful HTTP chat response alone is not proof that a comment appeared to viewers.

This is a connection-bootstrap change, not a promise that one additional endpoint cures every non-displayed comment. Do not send test comments during development without a separately specified live test.

## Evidence and limits (2026-10-21)

In an independent anonymous Chrome session on `@dyyoudaddy10/live`, the page requested `POST https://webcast.us.tiktok.com/webcast/room/enter/` successfully, then `GET https://webcast.us.tiktok.com/webcast/im/fetch/` with `client_enter=1`, `ws_direct=1`, and `cursor=0`. The fetch returned a protobuf `ProtoMessageFetchResult` with a nonempty cursor (53 bytes), 16 initial message envelopes, `push_server` pointing to a TikTok WSS endpoint, and route-parameter keys `imprp` and `wrss`. This is the same response structure TikTokLive expects from its sign-service proxy. No raw response, token, cookie, full URL query, or comment body is retained in this design.

The first Chrome sample was anonymous and did not itself prove authenticated parity, a WSS upgrade, or public comment delivery. The current direct-WSS profile uses a synthetic uninitialized environment and an empty cursor; the fetched response must not be combined with it and called browser-equivalent without a connection-level test.

Later anonymous SDK comparison established that `webmssdk 2.0.0.561` initializes two page-level values with a formula already present in the local `_gnarly_field8` helper. A fixed-input probe matched the formula exactly. The first value is used as X-Gnarly field 8 and the second as X-Dynosaur field 52 across a page session. The current local selectors instead supply constant values per request; merely adding the observed fetch route IDs `11/40` does not recreate this shared state. A separate in-memory browser probe proved X-Dynosaur field 44 and X-Gnarly perf data both equal the SDK's `wID.canvas` environment slot. The project currently uses a static `wID.canvas` fixture value for all three; the algorithm for generating an account/session-consistent canvas value has not been proven. The observed page `/web/report` used the US `mssdk.tiktokw.us` host and a longer token shape than the project SG report. Do not change the issuer solely from that anonymous comparison.

After an IP change on 2026-10-22, an isolated Chrome visitor page for `@manni0207` again received an accepted protobuf initial fetch on the generic webcast host, including cursor and WSS routing. The same room's saved-account `curl_cffi` chain had accepted enter but fetch HTTP 403. A same-page trace of 14 signed browser requests showed monotonically advancing signer counters and a transition from uninitialized 6/6-byte SDK fields to initialized 12/34-byte fields before the fetch. The initialized 10-character field matched the loaded `webmssdk_ex 1.0.0.2935` version; its neighboring 32-character field was stable across isolated profiles but was not MD5 of that script file. Fetch counter values changed across page loads, so the local fixed `11/40` values cannot be treated as endpoint constants. Browser visitor and saved account differed in this comparison, requiring the later identity-controlled check below.

The identity-controlled gate was met later the same day on a currently live room, `@ciniss`: an isolated Chrome profile with the saved `spider_king017` login cookies produced enter business status 0 and an accepted 30,829-byte initial protobuf fetch with cursor and route data. The outgoing session and UID cookies matched that saved record. Its fetch signer used page-wide request counters `21/50`, a nonzero initialized field40, a canvas field different from the local fixture, and `webmssdk_ex 1.0.0.2937`; the local code uses fixed `11/40`, zero/uninitialized enter-derived fields, and `1.0.0.2717`. Moreover, the accepted request's `msToken` query value and `msToken` Cookie were distinct 172-character values, whereas the local replay uses one 144-character report result in both places. A successful anonymous fetch reproduced the distinct-value pattern. Thus account and room access are established, but the local SDK/session state model is insufficient. Domain swaps, a field53-only change, and a fixed route-ID patch have already failed. Do not wire the existing static signer into production fetch or add another constant patch; revise the signer/session architecture and validate it on fixed inputs before any new account-bound replay.

A user-supplied standalone `example.py` provides a useful control, but its active path refreshes `msToken` and sends only `/webcast/room/enter/`, not `/webcast/im/fetch/` or WSS. It uses a different saved login and explicit room values. Its signed UA and `browser_version` say Chrome 150, while its `sec-ch-ua` says 136 and `curl_cffi` impersonates Chrome 120. An accepted enter therefore does not establish that these mismatches are safe for fetch, nor does it disprove the stateful-signer gap. The project already derives `browser_version` from the selected account UA for enter and fetch; the new session must additionally align Client Hints and transport impersonation with that same selected UA version, or fail explicitly if no matching supported transport exists.

## Stateful signing session design

Each account or anonymous observer owns one isolated `SigningSession` for its room-page lifecycle. The session carries its selected UA, matching `browser_version`, matching Client Hints, matching supported fingerprint transport, per-account Cookie jar, room/page URL, device/profile facts, page seed and canvas state, supported SDK manifest, signed-request counters, and separately tracked query-token and cookie-token provenance. No global counters, static page fingerprint, captured signature, or other account's state may be substituted. Values observed in one Chrome trace are test vectors, never production defaults.

`prepare(account, room)` selects and validates one coherent browser profile and establishes the fresh session. `sign_enter` and `sign_initial_fetch` use the same state object, sign the exact ordered URL and exact transmitted body, and advance counters only for actual signed operations in this session. `observe_response` updates cookies from responses under normal origin/domain rules. The minimal browser-free flow need not imitate every page analytics request merely to reach Chrome's observed counter values; its own sequence must instead be verified with fixed-input signature vectors and accepted live responses. SDK version changes are detected through a supported manifest, not permanently pinned to the last observed `1.0.0.2937`.

The existing Python `X-Dynosaur`, `X-Gnarly`, and report-building primitives are the first implementation choice. Isolate any irreducibly opaque SDK state behind a narrow, deterministic, browser-free local JS helper only after a fixed-input comparison proves Python parity impossible or disproportionate. Python remains responsible for HTTP, cookies, sequencing, response parsing, and WSS. Do not drive Chrome in production or call the TikTokLive signing service. A full SDK emulation is a later design alternative, not the default.

Token sources must be modeled separately. Browser evidence shows that the fetch query `msToken` and Cookie `msToken` may differ, while the current local code copies one report token into both; which writer, refresh event, or rotation produces each value is not yet established. Trace their provenance and test it before live replay. Likewise the generators for initialized signer field40, the version-adjacent field51, and page canvas/seed must be demonstrated by reproducible fixed-input vectors, not guessed from a single capture. When an input is missing, stale, or belongs to another account/page, the session fails closed.

## Proposed request flow

For each account send lifecycle or anonymous observer, keep a separate session and request budget. A sender's enter, fetch, WSS, and chat gate share one prepared identity; an observer cannot borrow it:

1. Resolve and validate the current room and destination host. For an account, use only that account's stored Cookie and User-Agent; for an observer, use only its independent visitor state. Never mix identities or copy cookies from the user's already-open browser.
2. Perform the existing first-party `room/enter` request in the relevant session where needed, checking both HTTP and business status. Do not treat a room-ended response as success.
3. Build the first-party `/webcast/im/fetch/` request from the same signing and HTTP session. Reproduce the observed ordered query shape and generate per-request dynamic fields with locally verified code; no captured signatures or dummy values. The initial cursor is `0` and `client_enter=1` only when the matching observed web flow requires them. An unsupported or missing signing input fails closed.
4. Decode the bounded protobuf response locally. Require nonempty cursor, validated `push_server`, validated route parameters, and matching room context. Preserve initial messages as historical events, not delivery evidence.
5. Construct the WSS URL from server-issued `push_server` and route parameters plus verified web parameters. Apply strict TikTok WSS destination and room checks. Enter, heartbeat, ACK, and subsequent comments continue through the existing bounded protocol and connection lifetime.
6. On failed fetch, malformed protobuf, missing route state, or account mismatch, report initialization failure and do not send chat POST for that account. Do not silently fall back to the old static direct URL or a third-party sign service.

## Module boundaries

- Add an isolated signing-session abstraction under `tiktok_live/` that owns one account/page's signer state, coherent browser profile, token provenance, and response-driven Cookie rotation. The existing `signing.py`, `algorithms/x_dynosaur.py`, `algorithms/x_gnarly.py`, and `algorithms/ms_token.py` remain its pure Python primitives after replacing fixed endpoint/session values with explicit validated inputs. `config.py` must not silently map an unsupported UA major to a different impersonation major for this flow.
- Add a narrow first-party fetch/parse module under `tiktok_live/wss/`; it owns HTTP bootstrap, response decoding, and a redacted result type, not account storage or chat posting.
- Change `tiktok_live/wss/sessions.py` to prepare account and visitor sessions with isolated state and a validated prepared connection.
- Change `tiktok_live/wss/connection.py` to consume the server-issued WSS destination and initial cursor instead of `build_direct_url` for this path.
- Extend `tiktok_live/wss/protocol.py` only for bounded initial-response protobuf decoding and any evidenced enter-frame/ACK fields. Reuse existing frame decoding where possible.
- Keep `tiktok_live/client.py` as the owner of room entry and chat HTTP; avoid duplicate account-bound entry requests when the sender and heartbeat already share a proven session.

## Evidence gates before wiring production

The identity-controlled Chrome acceptance gate is already met for enter and initial fetch. Next, prove a coherent browser profile, initialized signer fields, request counters, and query/Cookie token provenance with fixed-input vectors before another account-bound replay. Compare only field names, lengths, response status, and safe hashes in logs. Then require at least two independently accepted, fresh, browser-free initial fetches using the same account on an actually live room, followed by a validated WSS route, heartbeat, and ACK. If these cannot be reproduced, stop with a precise unsupported-state error; do not hardcode an observed signature, use the other browser account, or reintroduce TikTokLive's service.

The existing older full-SDK-initialization design records that the local frontier environment model is incomplete. This design addresses that gate through the scoped signing session. If a full SDK emulator or browser-backed production runtime becomes necessary, return to design review rather than expanding implementation silently.

## Safety, testing, and acceptance

- Parse synthetic protobuf fixtures covering valid cursor/push-server/route parameters, truncated or oversized fields, absent required values, and historical initial messages. Bound response bytes and decompression.
- Verify URL allowlists, room matching, HTTPS/WSS scheme, redirect handling, timeout/cancellation, and no secret-bearing values in logs or errors.
- Test parallel account and observer isolation, one session's cookie never entering another session or a third-party origin, and failure preventing chat POST.
- Test that the signed User-Agent, query `browser_version`, Client Hints major, and selected `curl_cffi` transport major agree. An unavailable fingerprint must yield an explicit unsupported-profile error, not nearest-version fallback. The standalone example's successful enter with Chrome 150/136/120 mismatch is not an acceptable parity test for initial fetch.
- Confirm exact initial request order and dynamic field generation on one live room with metadata-only capture. A successful WSS connection must receive expected server frames and send bounded heartbeat/ACK before chat is allowed.
- Separately, with the user's live-message authorization, send one marked comment and verify it through an independent observer by message ID, content, sender, and time. Record `observed` versus `not_observed`; do not call an unobserved comment delivered.
- Preserve existing user data and unrelated dirty-tree edits. No packaged release or success claim until targeted and full tests pass and a fresh live acceptance check is explicitly authorized.
